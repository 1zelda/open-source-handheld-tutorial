# 双流水线建设计划：AAA 逆向重建与原生移植

编制日期：2026-10-30。适用项目：F 盘“开源掌机教程”的移植工厂。

本文是建设计划，不是功能完成报告。本轮核实了上游项目及本地代码，没有安装新工具、执行上游构建脚本、运行商业游戏或完成真机测试。

## 一、结论：要建的是两条能衔接的工程产线

你的需求可以落实为：

1. **逆向重建产线**：输入指定版本的游戏程序，调用成熟反编译器或静态重编译器，让 AI 辅助恢复结构、补充接口和修复问题，输出有来源证据的代码工程。
2. **原生移植产线**：输入现成源码、已有重编译工程或第一条产线的工程，适配 Switch 1、Linux 掌机、Android，自动构建、收集故障、修复、回归、封装。

**这不是简单接一个模型接口就能完成的任务，应按本计划分阶段建设。** 可以自动化大量重复劳动，但首次适配新游戏、新引擎或新 GPU 后端，仍然是研发任务；不能承诺任意 AAA 输入一次提示词就自动得到完整、正确、流畅的全平台游戏。

推荐总方案：**Ghidra + GhidraMCP 做通用逆向入口，ReXGlue 做 Xbox 360 静态重编译主分支，现有 portkit 做构建封装底座，另补共享调度、AI 补丁闭环和运行验收。** 不再把自研小函数 IR 扩展成整款 AAA 的唯一主路。

成熟的是若干工具和特定游戏工程，不是“一套工具已成熟支持所有 AAA”。本轮核实到的项目，没有提供这种通用能力的可验证证据。

## 二、GTA5、GTA4 到底证明了什么

### 2.1 GTA5：脚本反编译、源码泄露、完整程序重建不能混为一谈

- `calamity-inc/GTA-V-Decompiled-Scripts` 的说明是反编译 `.ysc` 游戏脚本及 native 表。它不是完整 RAGE 引擎源码，也不是可直接移植的整款游戏工程。[S1]
- 另有 2023 年 GTA5 源码泄露报道；泄露不是反编译成果，更不能作为我们引入代码的合法来源。[S2]
- 未提供具体新闻链接，不能判断你看到的是哪一项；这两类常见材料均不能证明“通用 AI 已能完整反编译任意 AAA”。

### 2.2 GTA4 Switch：找到了实际工程与发布物，路线值得借鉴

核实到 `kabba536/Grand-Theft-Auto-IV-Native-Port-Nintendo-Switch`，存在 v35 Performance 和 v50 Quality RC1 发布物；仓库仍明确标为实验性，两个版本都不是完成版。[S3]

实际路线是：

```text
指定 Xbox 360 版本的 GTA IV
    → LibertyRecomp / ReXGlue：PowerPC 代码转 C++
    → LibertyRecompAndroid：Android 平台适配
    → Switch 分支：平台补丁、图形驱动接入、性能调整
    → devkitPro / libnx 构建 ARM64 原生程序
```

这里的输入要求是 **Xbox 360 USA 版及 Title Update 8**，不是任意 PC 版 GTA4 EXE。工厂必须识别并锁定版本，不能拿用户现有 PC 文件静默替代。

作者报告的 Switch 性能包括：v35 一般场景约 25–30 FPS、驾驶约 22–28 FPS；v50 一般场景约 20–25 FPS、驾驶约 17–24 FPS，部分场景更低。这些是上游报告，不是我们测得的数据，也不是全程稳定性能的证明。

CPU 走提前编译出的原生 ARM64 代码，但仍依赖源自 Xenia 体系的运行时语义和图形兼容工作。**“原生重编译”不等于恢复出 Rockstar 原始 C++，也不等于不需要兼容层；本项目不会把模拟器加镜像的包冒充原生移植。**

还要区分“仓库公开了源代码补丁”和“完整工程已审计可分发”：Switch 仓库的构建链依赖上游工程、生成代码、平台库与专属补丁，不能只看一个源码压缩包就判定交付完整。

### 2.3 AI 确实参与了这条链，但并非独立完成全部逆向

`vaduur/LibertyRecompAndroid` 作者明确表示，自己的移植代码主要由 Claude 编写，自己负责反复测试和反馈问题；同时感谢上游已完成的重编译工作。该分支当前标注暂停维护。[S4]

这说明“**成熟框架 + AI 写适配代码 + 人或设备提供测试反馈**”有真实先例，正是值得复制的工作方式；它不能证明单靠提示词就能从未知商业程序开始无人值守完成全部逆向与移植。

该 Android 分支主要围绕 Adreno/Turnip 验证，Mali/Immortalis 路径仍实验性。因此不能把 Android ARM64 支持直接等同于天玑设备支持，更不能等同于 Switch 支持。

## 三、工具选型：哪些知名，哪些接近产线

以下 star 为本轮 2026-10-30 查询的约数，仅反映关注度，不是正确性、许可或成熟度证明。

| 组件 | 关注度 | 放在哪里 | 能提供什么 | 关键边界 |
|---|---:|---|---|---|
| Ghidra | 约 9.6 万 | 产线 A 通用后端 | 多架构分析、反编译、调用关系、类型分析、P-code、中间证据 | 伪代码不自动等于可编译项目；原变量名、注释、源码结构通常不能完整恢复 |
| LaurieWired/GhidraMCP | 约 1.16 万 | AI 到 Ghidra 的工具桥 | 查询函数、反编译、重命名、导入导出信息；支持 PyGhidra 无界面模式 | 是工具接口，不是完整逆向与验收调度器 |
| ReXGlue SDK | 约 1,200 | 产线 A 的 Xbox 360 主分支 | PowerPC → C++ AOT 及相关运行时基础 | 上游自称早期开发，API 会变化；主线不能保证 Switch 可用 |
| XenonRecomp | 约 6,600 | Xbox 360 转译参考/备选 | 将 Xbox 360 程序转成可编译 C++ | 官方明确不提供完整运行时，游戏能工作仍需自行实现其他部分 |
| 360tools | 约 50 | 调度与适配配方参考 | 版本提示、兼容矩阵、失败归类、未解析调用修复循环、断点续跑 | 更接近工程工具箱，但关注度低、依赖 SDK 版本，不能直接当成熟通用成品 |
| devkitPro / libnx | 本地已接线 | 产线 B 的 Switch 后端 | homebrew 编译、平台接口、NRO 构建 | 不是任天堂官方商业 SDK，也不是商店上架流程 |
| Clang / CMake / Ninja | 按项目选用 | 两线的可复现构建 | 编译生成代码和平台运行时 | 版本、依赖、GPU 后端要与指定游戏分支匹配 |

推荐采用 Ghidra 与 ReXGlue 两个后端，而不是同时堆入大量同类反编译器。XenonRecomp、360tools 用于参考与必要补充，避免维护三套重复的 Xbox 360 产线。[S5–S9]

GhidraMCP 当前文档要求匹配的 Ghidra 版本，并给出 Python 3.10–3.13、Java 21 等环境要求；实施时锁定整组兼容版本，使用独立项目环境，不能假定装入现有 Python 环境就能工作。

已有游戏专用工程应优先复用。例如 GTA4 的 LibertyRecomp 链、使用静态重编译的 UnleashedRecomp，说明工程化路线存在；它们不代表同平台所有游戏都已经解决。[S10–S11]

## 五、整体架构与两线交接

```text
统一入口：游戏 / 源码 + 明确版本 + 目标设备 + 本次授权范围
    │
    ├─ 有可用源码或现成移植工程 ───────────────────────┐
    │                                                │
    └─ 只有二进制 → 产线 A                           │
          ├─ A1 Ghidra：分析、结构恢复、模块重建       │
          └─ A2 ReXGlue：特定平台静态重编译            │
                         │                           │
                 工程清单 + 验证证据                  │
                         └───────────┬───────────────┘
                                     ↓
                    产线 B：基线构建 → 平台适配
                          → 编译 → 运行回归 → 真机验收
                          → 最终封装 → 交付资格判定
                                     ↑
                    AI 补丁 ← 独立验证器的真实反例
```

A1 与 A2 是替代或互补路线，**不是要求先把所有生成代码美化成人写的源码，才能开始移植。** 有现成开放引擎或稳定移植工程的游戏直接进入 B；选择低成本路线不代表换成模拟器。

### 5.1 共用交接清单

以下是待实现的数据契约，不是当前已经支持的配置字段。

| 字段组 | 必须记录的内容 |
|---|---|
| 身份 | 游戏 ID、源平台、发行/补丁版本、输入逐文件 SHA256、任务 ID |
| 路线 | 现成源码 / Ghidra 重建 / Xbox 360 AOT，以及选用理由 |
| 工具 | 分析器、编译器、SDK、运行时的固定版本或提交；依赖锁与构建选项 |
| 代码类型 | `analysis_only`、`module_source`、`buildable_project`、`aot_project` |
| 工程 | 源文件清单、入口、构建配方、资产需求、生成文件与人工维护文件的边界 |
| 运行时契约 | ABI、地址模型、字节序、平台 API、图形/音频/输入/线程后端、未解决项 |
| 证据 | 原字节段、地址映射、反编译记录、反例、测试范围、输出哈希 |
| 资格 | 已达到的验证级别、阻塞项、支持的设备/功能范围、分发限制 |

`analysis_only` 和只有孤立模块的 `module_source` 不能伪装成整游戏工程送进 B。B 的入口必须验证入口程序、构建配置、依赖和运行时契约完整，再用实际构建确认可用。

### 5.2 共享调度原则

- 控制器维护任务依赖图，工具执行、AI 产出、验证、接受补丁分别记录，不让模型直接修改数据库通过状态。
- 阶段缓存键纳入输入内容、源码/补丁、spec、目标档案、工具版本及验证器版本；命中时还要核对产物存在且哈希一致。
- 只重跑受影响的阶段。比如打包说明变动不必重新分析所有函数；运行时变动必须触发相关编译和运行回归。
- 每轮 AI 修复使用独立工作副本；记录父版本、差异、反例与结果，拒绝的补丁不进入基线。
- 长任务采用明确的工具超时、模型预算、磁盘预算和编译并发限制；按实测资源调整，不无限自动重试。
- 游戏文本、字符串、日志和反编译注释都是待分析数据，不得升级为代理指令；分析服务仅本地开放并限制工具权限。

## 六、产线 A：从程序到有证据的代码工程

### A0：接收、识别与选择路线

输入原件只读；在 F 盘英文研发路径建立必要快照。大游戏按清单分阶段读取/复制，不把整个几十 GB 数据包塞进模型，也不把当前单文件研究入口的大小限制简单取消就当成支持 AAA。

输出：准确源平台、架构、版本、依赖和文件身份；可用上游工程清单；路线选择理由；授权/工具/版本阻塞项。

落地状态（2026-11-01）：这一格的“选路”已由 `port route` 实现——只读扫描文件名、构建入口、文件头与包内清单，产出路线、证据、阻断与下一命令；`port new` 只在判定为源码路线（`B-source`/`B-recomp`）时接着生成待填 spec，并把判定 JSON 的哈希写进草稿，二进制/数据/压缩包路线一律拒收且不留文件。快照与工程清单仍由 `port handoff` / `check-handoff` 承担。这两个命令都不解压、不执行，也不代替 A1/A2 的深度分析。

遇到壳、加密、DRM、缺失平台文件或版本不匹配时停在对应原因，不绕过，不偷偷换发行版。

### A1：通用逆向分支

1. Ghidra 无界面导入并保存项目，提取段、函数、交叉引用、导入、类型和反编译结果。
2. 给每个推断保留来源地址、原字节摘要和工具版本；函数发现结果不称为完整游戏覆盖率。
3. AI 通过受限工具查询局部上下文，恢复命名、结构体、接口关系和子系统边界；区分“推测”与“已验证”。
4. 对有明确边界的模块生成可编译实现和构建信息；通过编译器、契约测试及可用原行为证据逐步提升可信度。
5. 对全局状态、对象、间接调用等形成待解决依赖图；不靠删调用、返回常量或跳过功能来凑通过率。

现有 Unicorn 差分继续验证它确实支持的 x86 局部函数。它不承担整个操作系统、GPU 或整款游戏模拟，也不自动覆盖 Ghidra 支持的所有架构。

只有完成工程连接、依赖闭合和对应验证后，A1 才输出 `buildable_project`；否则如实输出研究工程及未解决清单。

### A2：Xbox 360 静态重编译分支

1. 锁定获授权的指定版本输入与兼容的 ReXGlue/游戏专用工程提交。
2. 调用固定版本的分析和代码生成工具，保留函数边界提示、跳转表、地址映射、shader 处理结果及生成日志。
3. 整合运行时、系统导入、线程同步、文件/资源访问、输入音频和 GPU 后端。
4. AI 优先处理函数提示、接口适配、构建配置与有反例的局部修复；不要无理由重写全部生成 C++。
5. 输出 `aot_project`，记录每一处未解析调用、未知指令、未实现 API 和图形降级项，交给 B 构建与验证。

生成代码原则上从固定输入和配置重新生成；手写扩展用 hooks、维护区或可重放补丁保存。确实要改生成器或生成结果时，记录补丁来源并验证再次生成不会悄悄丢失。

“不支持的调用先返回 0”“漏掉 shader 就跳过”可以暴露为研究期临时实现，但不得计为功能通过。只有明确限定为无行为影响且有证据的空操作，才可以不是阻塞项。

## 七、产线 B：从工程到目标设备的原生游戏

### B0：接收工程并建立基线

校验交接清单、依赖锁与来源；优先构建可信的宿主版本，形成最小可玩流程及日志基线。源码有 host 版本不代表可以启动来源不明的原 EXE；可信基线的执行环境和授权单独确认。

现成源码直接从这里进入，不强制跑 A。

### B1：设备能力预检与适配任务拆分

设备档案至少区分：操作系统、CPU/ABI、GPU/API/驱动、可用内存、输入设备、文件系统、部署方式。不能只写“ARM64”。

- **Switch 1**：devkitPro/libnx、手柄、存储、线程、内存、图形后端；本项目指 homebrew，不声称官方认证。
- **Linux 掌机**：具体 CPU/系统、glibc、图形 API/驱动、PortMaster 运行库与输入适配；不是所有开源掌机都够运行同一款 AAA。
- **Android/天玑**：NDK、JNI/Activity、包与资源、触控/手柄、生命周期、Mali/Immortalis 驱动；需要新增对应构建封装后端，不能沿用 Switch 配置。

GTA4 这类工程还涉及 Xenos 图形语义转换和 Vulkan 驱动适配。CPU 已能交叉编译不能推出 GPU 渲染正确，更不能推出性能达标。

### B2：受控 AI 补丁循环

```text
真实构建/运行失败
    → 故障归类和最小复现
    → AI 读取关联源码、工具文档和反例
    → 输出最小补丁及影响范围
    → 在隔离工作副本应用
    → 从真实构建入口重建
    → 定点复测 + 受影响回归
    → 接受成为新基线，或拒绝并记录原因
```

需要区分缺工具、源码编译错误、链接错误、平台 API 缺失、运行崩溃、玩法偏差和性能瓶颈；不能把所有问题都交给模型随机改代码。

控制器必须拒绝：补丁改到授权目录之外、删除验收项、放松闸门、伪造测试日志、把缺失功能变成默认成功、原样重交冒充修复。达到预算或没有真实进展就停止并提供可操作的阻塞清单。

### B3：运行与游戏回归

最小可玩流程必须包含实际交互，不只是启动菜单。依据游戏类型定义移动、战斗/驾驶、关卡切换、资源加载、音频、输入、保存和恢复等任务。

结合以下证据，而非只比较截图：

- 可固定时钟/随机种子时使用可重放输入和状态检查点；不能固定的系统使用事先定义的事件/行为判据。
- 画面、shader、字幕、UI 和音频的人工或半自动检查；图像相似度不是整游戏等价证明。
- 崩溃、未实现接口、内存峰值、帧时间分位数、读盘卡顿、长期运行和存档兼容记录。
- 不同渲染后端存在合理浮点差异时，按具体特性制定容差，不发明统一阈值掩盖问题。

平台共用修复回写共用后端；只适用某游戏/版本的内容保留在配方，不为下一款游戏复制一份工厂。

### B4：真机、封装与交付

真机自动化可以逐步加入远程部署、日志采集和输入回放；未接设备时，必须保留 `device_pending`，不能自动变成“已完成”。原型阶段可生成人工操作清单并接收绑定制品的录像/日志。

构建后可以先生成内部测试包用于部署；完成要求的运行验收后再封装最终交付包。最终包必须包含同一份已测二进制和配置，重新核验逐文件哈希，并从包本身做安装/启动抽检。

交付物包括：原生程序、允许分发的运行库、用户自备数据导入说明、对应许可证/来源清单、已测设备和已知限制、验收证据索引。游戏资产与生成代码的分发资格分别审查，不能仅凭工具许可证决定。

## 八、验收等级：防止“编出来了”冒充“移植成功”

以下是建议的统一里程碑，具体检查项从游戏/目标配方生成。

| 级别 | 达成条件 | 可以怎么说 |
|---|---|---|
| R0 输入固定 | 文件版本、哈希、路线明确 | 已登记、可以研发 |
| R1 分析/转换 | 分析或代码生成确实执行，未知项完整列出 | 已有逆向证据或生成代码 |
| R2 可构建 | 指定工具链真实编译链接，产物身份明确 | 编译成功 |
| R3 可启动 | 可信环境进入可交互程序，日志和制品绑定 | 已启动，未证明可玩完整流程 |
| R4 可玩切片 | 事先约定的一段真实玩法与存读档等相关功能通过 | 指定流程可玩 |
| R5 目标设备验证 | 真机运行、性能、输入/音频/加载及稳定性达到约定范围 | 该设备上的已测流程可玩 |
| R6 交付资格 | 声明的完整交付范围完成回归，最终包通过来源与完整性检查 | 在明确版本、设备及范围下可以交付 |

R4/R5 不得自动宣传为“整场战役已通关”。如果交付目标写的是完整游戏，必须事先建立主流程/关卡/关键系统覆盖计划，达到该范围后才能进入 R6；没有有限测试能够证明所有可能路径等价，报告仍须保留已知限制。

所有检查逐格记录 `pass / fail / blocked / not_run / not_applicable`；不适用必须有依据，未测试不得计为通过。功能关闭、分辨率下降、人口密度变化等必须是可见的适配决策，不能静默算作与原版相同。

性能目标先做代表性场景测量再定。不要先承诺所有 AAA 在 Switch 1 都稳定 30 FPS；若硬件能力不足，应给出测量和可选取舍，而不是让模型无上限优化。

## 九、实施批次与退出条件

这套系统可分批完成；“工厂能力建设”和“某款 AAA 达到成品”是两条进度，不能混成一个承诺日期。

| 批次 | 实施范围 | 验收后才能进入下一步的条件 |
|---|---|---|
| P0 共享契约与可信续跑 | 工程交接清单、统一任务身份、阶段依赖摘要、准确产物绑定、状态口径 | 改输入/补丁/工具版本会使相应阶段失效；旧 ZIP 和被改产物无法借旧绿灯通过；现有源码配方仍可运行 |
| P1-A 通用逆向接入 | 独立 Ghidra/GhidraMCP 环境、headless 导入、证据索引、受限 AI 查询与结果回写 | 对合法测试样本从真实入口产出可追溯项目；重命名等修改持久化；未构建的伪代码不会被 B 接收 |
| P1-B 构建修复接入 | 扩展 portkit 的故障结构、补丁副本、预算、真实重建与回归 | 一个可复现构建故障被真正修好；无效、重复、改闸门和破坏性补丁被拒；无进展能结束 |
| P2 Xbox 360 分支 | 固定 ReXGlue 及游戏专用工程、生成配置、运行时契约、交接 B | 对授权且版本匹配的样本完成真实生成和宿主构建；未实现接口如实阻塞；不能只用模型模拟输出 |
| P3 运行闭环与 Switch | 可信基线、交互检查点、日志/反例、平台适配、既有真机闸门接线 | 一个端到端真实项目达到 R4；具备设备时继续 R5，无设备则明确停住；通用调度不含游戏名特判 |
| P4 AAA 专项适配 | 以 GTA4 同类现成工程检验图形、资源、线程、内存和性能闭环 | 目标 AAA 的指定流程在目标真机达到约定标准；剩余任务/关卡和限制有真实清单 |
| P5 跨游戏与其他平台 | 第二个独立项目接入；Linux/Android 后端按需求推进 | 复用同一控制器和适配层，不复制工厂；第二个项目能暴露并验证共用能力，避免一款游戏专用脚本冒充通用线 |

### 推荐开工顺序

1. **先 P0**，否则 AI 每次改代码之后，旧缓存和旧包可能把结果验错。
2. **P1-A 与 P1-B 可以并行**：一边接成熟逆向器，一边把现有构建线接成能修复的循环。
3. P2 的工具/版本调研可并行准备；实际生成必须等输入、来源和所需执行环境就绪。
4. P3 的运行证据协议应尽早设计，不要到最后才发现“没有机器能验”。
5. 用现有开放源码项目校准机器，同时推进 AAA 分支；校准不是把最终目标降成小型老游戏。
6. 首个 AAA 优先选有公开重编译基础的版本，GTA4 路线作为工程参考；若当前只有 PC 版文件，不自动切换到 Xbox 360 版本，也不把它冒充同一路输入。

### 对本地代码的主要落点

- 研究调度层：扩展现有 research 的输入身份、任务和证据交接，不删除当前标量验证模式。
- 新增必要的 Ghidra 与 ReXGlue 适配模块：只封装外部工具的输入输出、版本和错误，不再自造通用反编译器。
- portkit 的 runner/spec：增加依赖身份、精确制品清单、AI 修复协调接口和运行验证交接；复用现有构建器、工具链档案与封装器。
- 现有 job/gates：复用任务及证据校验，增强制品/配置绑定，统一交付资格。
- CLI/看板：最终让用户只需提交游戏或源码、目标和预算，看到两线的阻塞点、证据与产物；新入口名称待实现时确定，本文不提供假装现已可用的命令。

每批只跑相关测试和实际生产入口验收，完成重要集成时再跑跨线回归。不要用临时脚本绕过产品路径，也不把全量测试绿灯当作游戏本身已经可玩。

## 十、哪些依赖和授权会影响落地

### 已有基础可复用

项目 Python 环境、现有研究调度、Zig 标量编译/Unicorn 差分、portkit、devkitPro/MSYS2 档案、基础包检查和真机证据机制。

### 实施前必须预检，不能默认本机已有

Ghidra 对应的 Java/Python 环境与 MCP 扩展；目标工程要求的 Clang/CMake/Ninja；ReXGlue 和各运行时依赖；Switch 图形后端；Android NDK 及封装环境；可信宿主运行环境；足够的编译内存和 F 盘空间。

GTA4 Switch 历史构建脚本使用 Linux/Docker 及 NVK 相关构建链。本机已有 devkitPro 不能推出整条链已满足；应先核对版本化依赖，再选择隔离构建环境。安装 Docker、启用虚拟化、改权限或全局配置都需要另行授权。

已读取的上游脚本包含清目录、强制重置仓库、全局 Git 配置和系统 Python 安装等操作。实施时必须审查并改为工厂自己的隔离构建步骤，不能原样执行到用户工作目录。

### 一直保留的边界

- 原游戏只读，工作副本在 F 盘；不删除用户游戏、素材或存档。
- 来源不明的原 EXE/DLL 不在宿主直接运行。后续完整行为比较须使用获授权、可信且隔离的基线；否则记录未验证。
- 不获取泄露源码、不绕 DRM、不处理或上传密钥/BIOS/凭证，不自动下载商业游戏整包。
- 默认本地处理商业程序证据；外部模型若需要源片段，先获得相应授权，不因安装 MCP 就视为允许上传。
- 外部源码、构建脚本、生成代码、依赖和最终包都需来源记录。工具开源不代表它处理出的商业代码和资源可公开分发。
- 安装插件、修改模型/网络权限、部署真机、对外发布分别确认；本计划不等于授权执行这些动作。
- 当前工作目录不是 Git 仓库，不为实施计划自行初始化、提交或推送。补丁比较与回退先使用独立快照；确需独立版本库时再明确范围。

## 十一、可直接用于实施的两份 AI 工作指令

这些指令要交给具备已批准工具权限的执行代理。它们用于推动实现与验证，不是“万能反编译提示词”；没有工具和反例反馈时，单独粘贴不会产生完整 AAA。

### 指令 A：建设逆向重建产线

```text
你负责本项目的逆向重建产线。目标是接入成熟分析/静态重编译工具，
输出来源可追溯的代码工程，并与现有 portkit 交接，而非再写一份泛泛方案。

先核对当前代码和工具环境。在授权范围内直接实现已就绪部分：
复用现有输入哈希、预算、锁和研究证据；接入 Ghidra 的无界面分析；
建立工程交接清单，明确区分 analysis_only、module_source、
buildable_project、aot_project。Xbox 360 分支使用固定版本的
ReXGlue/游戏专用工程，不能把 PC EXE 当作 XEX 输入。

保留函数地址、原字节摘要、工具版本、类型推断依据、生成配置、
运行时依赖和未知项。原生成代码与维护补丁分开，结果可以重复生成。
使用项目真实入口处理合法测试样本，并验证产物与源快照的绑定。
原有 x86 标量差分只用于它支持的范围，不冒充整游戏验证。

原件只读，不运行来源不明的游戏程序，不上传商业整包或秘密信息。
缺工具、权限、匹配版本或执行环境时报告具体阻塞，继续其他可做的独立工作；
不擅自安装、改全局配置、改验收规则或伪造代码生成结果。
交付实际代码改动、真实运行证据、已实现能力与下一项阻塞。
```

### 指令 B：建设原生移植与修复产线

```text
你负责本项目的原生移植产线。以现有 portkit 和 devkitPro 接线为基础，
直接实施共享制品身份、可信续跑、AI 补丁闭环和运行证据交接。
不要复制一份新构建器，也不要只返回方案。

首先使阶段状态绑定输入、源码/补丁、spec、目标、工具和验证器版本，
并让验证阶段读取本次构建封装的确切产物及哈希，拒绝旧包混入。
随后实现真实构建失败 → 局部补丁 → 独立副本重建 → 定点回归
→ 接受/拒绝的受控循环。重试有预算，重复或无进展补丁必须停止。

平台共用修复进入共用层；游戏专属内容留在版本化配方。
补丁不许删除验收项、改绿状态、用常量返回冒充功能或静默关闭渲染。
将现有真机证据闸门与制品哈希关联；没有设备就停在待验收，
不能把 NRO 头检查、编译通过或菜单截图称为完整游戏可玩。

从现有可信源码项目验证真实入口，保留未来 AAA 运行时接入能力。
原始素材、存档和用户工作保持不变；安装工具、运行未知程序、
部署设备或发布产物前取得相应授权。
交付可复用实现、生产路径验收证据和明确的未实现范围。
```

## 十二、最终交付目标与本轮交付

建设完成后的工厂应交付三类成果：

1. **两条可重复执行的产线**：共用身份、证据、预算和控制器，不靠每个游戏单独手工串命令。
2. **可维护的代码工程**：固定来源与工具版本，原生成代码、平台运行时、通用适配和游戏专属补丁边界明确。
3. **经明确范围验收的目标包**：真实设备和功能证据绑定最终制品；未完成的工作不能被“已打包”遮住。

本轮交付的是这份有上游证据和本地代码落点的建设计划。没有宣称双流水线已经建成，也没有宣称 AAA 已能全自动移植；下一步应从 P0 开工，再并行推进 P1-A/P1-B。
