一、你提到的问题（归成三层）
知识层

模型不懂游戏机制：热血足球一角色一必杀（23 个 = 日本队 12 + 对手 11），头球/倒钩全员通用，滑铲/跳跃属性逐人不同。让一个角色反复试，试到死也凑不齐全盘点——必须换人。这条记忆里已有攻略+官方说明书双证，但采集脚本没按这个知识设计。
时机问题：你的判断对——这个可以靠"多变体测试 + 记录"穷举解决（暂停秘技的按压节奏就是这类），它和机制问题是两种病，不该混在一起盲扫。
环境层

缺"训练场"：拳皇有 training mode、2v2 不管 2P 就能随便试；热血足球没有现成训练模式，就得靠金手指/存档造一个：冻结对手、固定球位、进禁区、把球传到目标角色脚下。现在没有这层，试错全程被比赛干扰。
换角色、选场景这些前置操作不会做：这是机制知识的另一半——不光知道"小辫子才有燕返"，还得知道"怎么把控制权交到小辫子脚下"。
覆盖层

"无法用 TAS 操控"报错 = 配套件缺失：每个游戏需要四件套——TAS 回放/输入代码、宏指令、金手指表、对应版本的 ROM。缺任何一件就报"不支持"，所以支持的游戏少。
金手指没被代码自动调用：零件其实存在（statebuild.py、retro\_cheat\_runner.py、statejump.py），但按你的实际体验，采集流程里没有自动调起来，人工成本高。
二、你没提、但我认为同样致命的
缺"成功签名"判定：打完一套输入，怎么知道必杀真的出来了？现在靠人看画面。每个要素需要一个机器可验的签名（画面特征或内存值——比如暂停秘技的签名是得分框"必杀技OK"文字）。没有它，"跑完了"≠"采到了"，自动化就是空转。
缺状态读取（内存地图）：要自动换人、判断"当前控的是谁、球在不在禁区"，得能读游戏内存。游戏数据字典/expanded\_50\_games\_memory\_maps.json 有雏形，但没覆盖/没验证的地址等于盲打。宏 + 金手指是"手"，内存读取是"眼"，现在只有手没有眼。
版本身份没有先行绑定：金手指地址、内存地图、指令表全都随 ROM 版本变。KOF98 ECK 那次就吃过亏——拿 98UM 官方指令表当 ECK 卡的权威，全错。正确顺序是：先验 ROM 指纹（sha1/set）→ 再查对应版本的三张表，查不到就报"需补"，而不是拿错表硬跑。
失败归因缺失：开不出必杀时，分不清是输入错/时机错/角色错/场景错/版本错/后端不支持。热血足球"版本删了必杀"的误判（后来撤回）就是这个病的代价——没有归因决策树，只能盲扫烧轮次。
模拟器后端能力不齐：BizHawk / FCEUX / RetroArch 对金手指、存档、逐帧、内存读写、Lua 脚本的支持各不相同。很多"游戏不支持 TAS"其实是后端没暴露接口，换后端或换加载方式就能解。需要一张"后端×能力"矩阵，报错时先查这张表而不是判游戏死刑。
知识包没有"入包前验证"工序：现在设计是 LLM 离线写逐游戏知识包、运行时零 LLM——方向对，但写进包里的机制知识本身没被探针验证过，错知识会被流水线批量复制（版本论就是例子）。应该是：攻略/官方来源 → 写成候选知识 → 探针实测确认 → 才进包。
采集台账与续跑：全必杀盘点 = 23+ 条 × 各自的成功签名，需要台账记"谁/哪招/已验证/对应片段"，补缺式续跑，采过的不重采。不然每次失败都从头来。
半自动的人工介入点没有显式设计：哪些环节必须人点头（机制确认、签名确认），哪些全自动，应该明说。现在的体验是"要么全自动、要么报错甩给人"，中间没有"系统把候选方案摆好、人只选一下"这档。
一句话方向
把管线从"输入序列回放器"升级成"知识驱动的状态构造采集器"：版本指纹定身份 → 验证过的知识包定"谁/在哪/按什么" → 金手指+存档造无干扰实验环境 → 内存读取当眼睛 → 成功签名当验收 → 台账续跑。金手指自动调用（第 6 条）只是其中一环，单独修它治不了热血足球这种病。
这个是我总结的问题 拿热血足球举例 但其实针对每个机型游戏 尤其是 街机 FC SFC GBA这类之后可能盘点制作视频比较频繁 有望制作出好作品的视频 我希望能够攻坚 能够攻克以上提到的这些问题 ，你觉得问题还有哪些 应该怎么解决 有没有现成的资源和项目 帮我穷尽搜罗齐全不要漏网 然后该怎么优化升级

## 二、在你列出的问题之外，还必须补这些制度



### 1. “完整盘点”必须先有可核对的名单



每个格子要明确：



> 哪个版本 → 哪个角色／形态 → 哪个要素 → 哪种必要变体。



例如热血足球：



- 逐角色射门必杀是一张表。
- 通用头球、倒钩等动作是另一张表。
- 守门扑救技另列。
- 不同输入能触发同一招，不自动算两个要素。



**完整度来自权威名单逐格对账，不来自把 `expected_total` 写成多少。**



### 2. 知识不能只有一个“已验证”标签



至少分清四种事实：



1. 文献记载存在。
2. 适用于当前游戏版本。
3. 当前采集方法可以复现。
4. 已有合格视频素材。



“有攻略但没复现”不等于攻略错；“脚本没打出来”更不等于游戏删了这招。



### 3. 金手指不是统一的“地址＝数值”



需要区分：



- CPU 总线地址与模拟器内存域偏移；
- 8／16／32 位、大小端、位掩码；
- 一次写入、每帧冻结、条件写入；
- RAM 修改、ROM 读取替换；
- 多行指令、指针、不同码制。



**优先让对应模拟器解释原生作弊码；只有确认支持的码型，才转换成统一补丁。**不能先压扁成字节，再希望各游戏自己适应。



### 4. 训练环境不能把要展示的机制一起破坏



“冻结对手”不是通用答案。



- 展示守门扑救，需要正常来球和碰撞。
- 展示反击，需要对手按预定方式攻击。
- 展示掉落，需要保留击杀和掉落流程。
- 设置持球者，可能还要同步球的位置、速度和角色动作状态。



正确方式更接近：



> 设置必要条件 → 核对条件 → 释放影响机制的修改 → 让游戏自然触发 → 验证。



**准备阶段直接写出的“成功标志”，不能再拿来证明动作成功。**



### 5. 固定帧宏应升级为“观察后行动”



不是：



> 跑 30 帧 → 跳 14 帧 → 射门。



而是：



> 确认角色 → 确认持球 → 到达区域 → 等待所需高度／动作阶段 → 输入 → 检查结果。



时机搜索仍然有用，但应只搜索有意义的参数：提前几帧、按多久、间隔多久、站多远，而不是把角色、场景、版本错误一起丢进暴力穷举。



### 6. 验收必须分成三个结果
























| 结果 | 回答的问题 |
| --- | --- |
| 动作成立 | 发出来的是不是指定招式？ |
| 效果成立 | 命中、破防、反射、变身、获得物品等是否发生？ |
| 拍摄合格 | 画面是否清楚、过程是否完整、声音是否同步？ |



**掉血不等于指定必杀；空放也不一定是失败。**纯展示动作和展示伤害效果，本来就是不同拍摄任务。



判据除了正例，还应有：



- 普通攻击；
- 错误角色；
- 相似但不同招式；
- 资源不足；
- 被防御／未命中；
- 菜单、读档、回合切换。



而且**标定用的样本与最终验收样本要分开**，不能用同一对截图既造尺子又证明尺子准。



### 7. 同样的存档名，不代表同样的环境



除了 ROM，还要绑定核心、模拟器构建、BIOS、区域、DIP、控制器、SRAM／NVRAM、补丁、初始随机状态。



- 不同核心的存档一般不能直接交换。
- 原版与练习 hack 的存档不能默认互通。
- 同为 BK2，也不自动表示跨工具兼容。
- 换了核心，旧“后端通过”报告不能无条件继续算数。



### 8. 模拟帧、输入帧、录像时间不是一条轴



街机不能统一写死 60fps；画面重绘一次，也不一定等于游戏逻辑前进一次。



建议分成两段：



- **探索段：**快速试验，保存输入、状态和观察结果。
- **正式录制段：**在相同验证环境中重放成功路径，录同步原声、干净画面。



不要用桌面等待时间拼出“看似正确”的录像时长。



### 9. 台账必须保存证据，不能只保存“绿灯”



现有台账已有指纹、产物校验和续跑，不用重造。但建议补上：



- 每次尝试使用不可覆盖的证据目录；
- 台账原子写入，避免并发互相覆盖；
- 采集、判定、导出分别缓存；
- 改判据优先重验旧素材，不必全部重录；
- 判定不明确的产物可以留存，但不能计入通过数。



### 10. “能自动采到”与“值得做成视频”要分开



你的目标不是机器人跑分。因此还要有一份**拍摄要求**：



- 观众需要看清什么差别；
- 动作之前需要多少交代；
- 是否需要普通版／特殊版对比；
- 哪一帧支撑解说中的哪句话；
- 是否残留调试字、训练菜单、遮挡；
- 这一组素材能否组成有节奏的完整盘点。



**技术通过只是素材入库条件，不是作品质量证明。**

## 三、建议的系统结构：保留现有底座，补成闭环



```
版本身份
   ↓
要素名单与来源
   ↓
选择采集路线
   ├─ 现成输入回放
   ├─ 验证存档＋动作配方
   ├─ 训练脚本／练习补丁
   └─ 人工示教一次
   ↓
构造前置状态 → 观察确认 → 执行动作
   ↓
动作判定＋效果判定＋困难反例
   ↓
正式有声录制＋画面验收
   ↓
逐要素台账 → 只补缺项
```



### 通用化应放在哪里？



**第一层：平台适配。**统一推进、按键、读写、存档、录音录像和能力报告。



**第二层：游戏类型模板。**
































| 类型 | 应复用的能力 |
| --- | --- |
| 格斗 | 朝向、距离、资源、硬直、木偶防御／反击、动作与连接事件 |
| 球类／多人控制 | 角色身份、控制权、球权、区域、球高、交接 |
| 横版动作／射击 | 武器、弹药、敌人、检查点、投射物、命中 |
| 变身／能力展示 | 形态、能力解锁、环境条件、持续状态 |
| RPG／收集 | 队伍、装备、事件旗标、掉落与实际获得、分支条件 |



**第三层：逐游戏包。**只保存这个游戏的角色表、地址、配方、判据和来源。



新游戏尽量只增加第三层；反复遇到的机制再抽进第二层。不要为了某一招在通用代码里不断加游戏名判断。



### 暂时不建议走的重路线



- 不把逐帧调用视觉大模型作为默认眼睛。
- 不把强化学习训练当普通招式采集的前置条件。
- 不要求先完整反编译整个游戏。
- 不同时维护所有模拟器为正式生产后端。



**有限搜索、可靠状态观察、现成训练脚本、一次示教，通常更便宜也更容易验收。**

| **FC** | 继续复用现有 BizHawk 路径 | FCEUX；Mesen 系用于调试 | 旧 Lua、输入电影和地址语义不能直接跨工具套用 |
| **SFC** | 优先把 BizHawk 接入同一契约 | Mesen 系、lsnes；Snes9x 按历史资产选择 | 肩键、内存域、子帧输入、存档与影音需要单独验证 |
| **GBA** | BizHawk 统一入口，mGBA 做专项补充 | TASVideos 脚本、逐游戏逆向资料 | 总线地址与 EWRAM／IWRAM 偏移必须明确；持久化存档恢复也要验 |
| **街机** | **先保留现有 FBNeo 产线**；MAME 作为新增覆盖与调试候选 | 专用训练 Lua、MAME debugger／宏 | FBNeo 独立版 Lua 与 libretro 核心不是同一接口；MAME 驱动存档能力也不齐 |



这里有几个容易踩的坑：



- 本项目目前展示平台配置中只有 NES 标为已验证；**上游支持 SFC／GBA，不等于本项目已经接通。**
- MAME 的存档操作是异步排程，不能调用后立刻假设加载完成。
- RetroArch 不会自动获得独立 FBNeo 的 Lua 训练脚本能力。
- stable-retro 很适合借鉴数据组织和已有初态，但随机动作示例不是要素采集器。
- SourMesen/Mesen2 已归档，README 指向 **MesenCE**；不能继续把旧仓当当前维护主线。



**不建议现在为追求“统一”先迁移整个街机产线。先让现有成功路径继续生产，再让新后端经过准入测试。**

## 五、优化升级顺序与验收口径



### 第一阶段：先消除假完整、假支持、假成功



优先处理：



1. 按权威名单重建要素分母。
2. 纠正资源目录、数量、平台标签和失效索引。
3. 修金手指语义及主执行路径断点。
4. 自动标定只能生成候选判据，不能自动升级为已验证。
5. 强制区分动作成立、效果成立和拍摄合格。



**验收：**普通射门不能冒充必杀；错误版本不能套地址；只有候选资料不能显示“已支持”。

**实施记录（2026-11-25）：**第 4、5 项的代码闸门已接通：自动标定只生成候选，正式 showcase 强制区分动作成立、效果成立、拍摄合格，任一失败或证据不足均不交付；拍摄检查覆盖全部正例帧。三个真实检测器已按新契约复验：红魂 35（90 帧）和黄魂 10（226 帧）通过，红魂 47（90 帧）因第 81—89 帧爆炸闪白超过拍摄亮度上限而拒绝写包，旧单帧晋升报告曾漏检这 9 帧。确定性回归已通过，但真实素材的指定动作身份、玩法效果与声音同步尚未逐项验收，不能据此把第一阶段标记为全部完成；GBA 平台生产闸门仍关闭。权威来源名单、资源目录与数量、金手指语义及主执行路径断点仍按第 1—3 项继续核验。

**窗口修正复验（2026-11-25）：**检测器晋升现按 `trigger.macro + trigger.extra` 计算正式采集窗口，窗口内逐帧检查、缺帧拒绝，窗口外侦察帧保留但不参与交付。红魂 47 作为动作专用素材，使用 `Up+B + extra=41`，只交付 f0000—f0041 共 42 帧；原始 90 帧侦察记录及其中 9 帧爆炸闪白拒绝证据均保留，拍摄阈值未放宽。新副本已实跑通过：红魂 35（90/90）、红魂 47（42/42）、黄魂 10（226/226）的动作、效果（均显式不适用）、拍摄三类判定全部 pass。晋升自检 16/16，主回归 1551/1551；新报告仍为 `platform_verified=false`、展示计划 `blocked / unsupported_capability`。该结果不证明红魂 47 的完整爆炸效果、伤害、资源消耗、技能语义或声音同步；这些边界与 GBA 平台闸门继续保持未完成/关闭。配方、输出包、报告及 SHA256 已写入《晓月圆舞曲_RAM校准缺口与复用方案_2026-11-25_检测器固化.md》第 20 节。



### 第二阶段：接通训练状态与闭环操作



复用现有状态构造和会话接口，补上：



- 角色／装备／场景选择；
- 前置条件观察；
- 准备、释放、动作、复位；
- 可复用的人工示教资产。



**验收：**从新进程加载初态，仍能确认正确角色与条件；修改之后游戏能正常演化，而不是只改了显示。



### 第三阶段：把“成功动作”变成“正式素材”



接同步原声、干净画面、动作始末窗口、字幕与解说证据对应，保留不可变尝试记录。



**验收：**看真正导出的片段，不能只看日志或单张证据图；中断后只补缺项。



### 第四阶段：用不同机制证明可泛化



建议的验证组合是：



- FC 热血足球：角色与球权。
- 街机现有明确版本的拳皇：格斗动作与效果。
- 街机横版射击：武器／投射物。
- SFC 洛克人X或超级银河战士：能力／装备。
- GBA 晓月圆舞曲：魂／装备／事件。



这是**建议验证矩阵，不是已跑通名单**。已经通过且指纹未变的格不重复跑；每类成熟后，再接一个未参与设计的游戏，检查是否只增加知识包就能工作。
