# 代码级解剖：一个真实移植仓库里，到底改了哪几处

> 面向完全没写过 C 的人。全文只讲一个仓库：**`orktes/max_arm64`**（把 Android 版《马克思佩恩》跑到掌机上的那个项目），
> 每一个结论后面都给**文件名 + 行号**或者**实测字节数**，你可以自己打开对。
> 样本副本：`F:\开源掌机教程\_scratch\port_code\max_arm64-main\`（zip 原件 22,944,719 B，解出来 109 个文件）。
> 上一篇《00-移植是怎么回事》讲的是概念和装机；这一篇讲的是**代码**。
> 想自己动手编一个端口，看下一篇《02-交叉编译与打包》。

---

## 一、先说这个项目最反直觉的一点：它几乎没有"移植"游戏本体

普通人以为移植 = 把游戏的 C++ 源码拿去给 ARM 编译器重新编一遍。
但《马克思佩恩》原版源码并不公开，重编无从谈起。

这个仓库干的是另一件事：

> **Rockstar 自己已经发布了 ARM64 的编译产物 —— 就是安卓 APK 里的 `lib/arm64-v8a/libMaxPayne.so`。
> 移植者不重写游戏，而是写一个"壳程序"，在运行时把这个 `.so` 读进内存、自己完成链接、
> 然后把其中几个函数换成自己的实现。**

你的 XF45V 是 RK3326，4 个 Cortex-A35，就是 ARMv8/AArch64。
**安卓手机用的指令集和你这台掌机是同一族**——这才是"安卓老游戏能上开源掌机"的全部底层原因。

于是整个工程被拆成三块，代码量一目了然（实测字节数）：

| 块 | 文件 | 大小 | 干什么 |
|---|---|---|---|
| 加载器 | `src/so_util.c` | 16,350 B | 把 `.so` 读进内存、重定位、解析导入、改内存权限 |
| 替身实现 | `src/imports.c` + `src/hooks/*.c` | 18,277 + 48,086 B | 提供游戏真正需要的函数（图形/声音/手柄/文件） |
| 装配线 | `src/main.c` | 7,311 B | 按顺序把上面两块串起来，再调进游戏主循环 |

`src/hooks/` 三个文件实测：`game.c` 28,997 B、`openal.c` 11,737 B、`opengl.c` 7,352 B。

**换句话说：真正"写给掌机的代码"，只有 8 万来字节。** 剩下的活儿是打包脚本和数据搬运。

## 二、"钩子"是什么：改 4 条指令就能换掉一个函数

这是全篇最该看懂的一小节。看 `src/so_util.c:75-83`：

```c
void hook_arm64(uintptr_t addr, uintptr_t dst) {
  if (addr == 0)
    return;
  uint32_t *hook = (uint32_t *)addr;
  hook[0] = 0x58000051u;           // LDR X17, #0x8   —— 把"往后第 8 字节"里的 64 位整数读进 X17
  hook[1] = 0xd61f0220u;           // BR X17          —— 跳到 X17 指向的地址
  *(uint64_t *)(hook + 2) = dst;   // 那 8 字节就是新函数的地址
}
```

白话：在旧函数的**第一行**塞一条"往后看 8 个字节，把那个数当地址跳过去"。
于是 CPU 一进旧函数就被拐到新函数里了，游戏自己完全不知道发生了这件事。

同文件里还留着 32 位 ARM 和 x86_64 的对应写法（`hook_thumb` `:51`、`hook_arm` `:66`、`hook_x86_64` `:85`），
说明这套代码是从 Switch/32 位安卓移植一路演化来的。

### 但代码段本来是"只读+可执行"的，凭什么能改？

`src/so_util.c:98-116` 就是干这个的：

```c
void so_make_text_writable(void) {   // 把代码段临时改成 可读写+可执行
  ... mprotect(text_virtbase, text_asize, PROT_READ | PROT_WRITE | PROT_EXEC) ...
}
void so_make_text_executable(void) { // 打完补丁再改回 只读+可执行
  ... mprotect(text_virtbase, text_asize, PROT_READ | PROT_EXEC) ...
}
```

`src/main.c` 里能看到严格的调用顺序（`so_make_text_writable()` → 三个 `patch_*()` → `so_make_text_executable()`）。
改完机器码还要让 CPU 别再拿缓存里的旧指令，`src/so_util.c:118-123` 用
`__builtin___clear_cache()` 刷指令缓存。
**这三步（放开权限 → 打补丁 → 收回权限 + 刷缓存）是所有运行时 hook 的通用套路，Windows 上的 mod、
Switch 上的补丁、掌机端口，全是一个形状。**

## 三、必改点逐个拆（这才是"移植要改什么"的标准答案清单）

### 必改点 ①：入口 —— 谁来启动游戏主循环

`src/main.c` 的 `main()` 里，程序并不自己写游戏循环，而是**从 `.so` 的符号表里把游戏的三个函数抠出来**：

```c
uint32_t (*initGraphics)(void) = (void *)so_find_addr_rx("_Z12initGraphicsv");
int (*ShowJoystick)(int show)  = (void *)so_find_addr_rx("_Z12ShowJoystickb");
int (*NVEventAppMain)(int argc, char *argv[]) = (void *)so_find_addr_rx("_Z14NVEventAppMainiPPc");
...
initGraphics();
ShowJoystick(0);
NVEventAppMain(0, NULL);   // ← 从这里开始就再也不回来了，游戏在自己的循环里跑
```

那串丑名字 `_Z14NVEventAppMainiPPc` 是 C++ 的名称改编（name mangling）：
`NVEventAppMain` + 参数 `int` + `char**`。
**做移植时你得先用 `nm`/`objdump` 在 `.so` 里找到真正的入口符号名，然后照抄。**

`so_find_addr_rx` 和 `so_find_addr` 的区别（`src/so_util.c:478` 与 `:513`）很阴险，值得记：
一个返回 `text_base + st_value`（用于**读写数据**），一个返回 `text_virtbase + st_value`（用于**跳转执行**）。
混用会在开 W^X 的机器上直接段错误。

### 必改点 ②：加载与链接 —— 自己当一次动态链接器

正常程序靠操作系统的 `/lib/ld-linux.so` 加载库。这里偏不：`so_load()`（`src/so_util.c:166`）自己读 ELF：

- `:200` 先验魔数 `ELFMAG`；
- `:221` 验 `EI_CLASS == ELFCLASS64`；`:227` 验 `e_machine == EM_AARCH64`（183）——
  **这就是"32 位安卓包在这台机器上跑不了"的代码级原因**；
- `:279-302` 扫程序头，按 `PF_X`（可执行标志）区分代码段和数据段；
- `:333-350` 把两段 `memcpy` 到 `main()` 事先 `mmap` 好的一大块内存里（`MEMORY_MB`，见 `init_heap()`）；
- `:380` `so_relocate()` 处理 `R_AARCH64_ABS64 / RELATIVE / GLOB_DAT / JUMP_SLOT` 四种重定位；
- `:421` `so_resolve()` 把"库里没有的外部函数"换成 `src/imports.c` 提供的替身。

`:439-440` 有个很实用的小花招：

```c
if (taint_missing_imports)
  *ptr = rels[j].r_offset;   // 故意把没实现的函数地址写成一个非法值
```

注释写着 "make it crash for debugging"：**没实现的导入不给你悄悄返回 0，而是让它一调用就崩**，
这样你就能立刻看出"哦，原来这游戏还用到 `xxx` 这个函数，我还没替它写"。
调试移植时这比打印 100 行日志有用。

### 必改点 ③：显示后端 —— 安卓那套 EGL 调用换成掌机这套

游戏里写死的是 NVIDIA 移动端引擎（NVEvent）的四个 EGL 函数。`src/hooks/opengl.c:196-208`：

```c
void patch_opengl(void) {
  hook_arm64(so_find_addr("_Z14NVEventEGLInitv"),        (uintptr_t)NVEventEGLInit);
  hook_arm64(so_find_addr("_Z21NVEventEGLMakeCurrentv"), (uintptr_t)NVEventEGLMakeCurrent);
  hook_arm64(so_find_addr("_Z23NVEventEGLUnmakeCurrentv"),...);
  hook_arm64(so_find_addr("_Z21NVEventEGLSwapBuffersv"), (uintptr_t)NVEventEGLSwapBuffers);
}
```

四个函数被换成了走 **SDL2 + EGL/GLES2** 的实现。编译链接依赖里能看到
`pkg_check_modules(EGL ...)` 和 `pkg_check_modules(GLESV2 ...)`（`CMakeLists.txt`）。

掌机固件的图形栈很杂，所以 `src/wrappers/gbm_wrapper.c` 干脆**不硬链** GBM/DRM，而是运行时试探：

- `:22-25` 先看 `/dev/dri/card0` 存不存在；
- `:35-43` 用 `dlopen("libgbm.so.1")`，失败再试 `libgbm.so`，再失败就 `return 0`（**"不是错误，只是没有"**）；
- `:46-56` 逐个 `dlsym` 取 11 个函数指针，`:59-66` 缺关键的就整体放弃。

> **给小白的一句话：** 同一份端口在 ArkOS / muOS / Knulli 上表现不一样，
> 十有八九就是这个探测层在你那台机器上没探到东西。看端口目录里的 `log.txt` 是唯一办法。

还有一处特别贴合你这台机器的代码：`src/main.c` 的 `check_for_4x3()`。
它打开 `/dev/fb0` 用 `FBIOGET_VSCREENINFO` 读真实分辨率，算宽高比：

```c
float aspect_ratio = (float)screen_width / (float)screen_height;
if (aspect_ratio < 1.4f) {          // 4:3 这种"矮胖"屏
  *(uint8_t *)so_find_addr("Use4x3") = 1;
  *(uint8_t *)so_find_addr("WideScreenRenderHack") = 0;
  ...
}
```

XF45V 是 **1024×768 = 宽高比 1.33**，正好落进 `< 1.4` 这一支，所以它会自动切回 4:3。
**这不是配置项，是运行时读 framebuffer 决定的**——所以你在这台机器上不用手动调宽高比。

### 必改点 ④：输入 —— 游戏只认安卓触屏，得把"手柄"喂成它认识的东西

`src/hooks/game.c` 里（行号取自实测 grep）：

- `:60` `static SDL_GameController *gamecontroller = NULL;`
- `:78-100` 遍历 `SDL_NumJoysticks()`，用 `SDL_IsGameController(i)` 挑第一个合法手柄并 `SDL_GameControllerOpen`；
- `:320-356` 直接把 `DPAD_UP/DOWN/LEFT/RIGHT` 写回游戏的方向状态；
- `:403-405` `SELECT + R1` 组合键当"快速存档"；
- `:387-389` `SDL_PollEvent` 里抓 `SDL_QUIT`。

`:116-122` 还包了一层 `safe_hook_arm64()`：**符号不存在就跳过，不报错**。
因为安卓 1.7 和 2.x 的 `.so` 符号表有差异，硬要求某个符号存在会让端口在别的版本上直接起不来。

### 必改点 ⑤：声音 —— OpenAL 设备句柄的"偷梁换柱"

`src/hooks/openal.c` 只钩了两个函数（`:191`、`:174`）：

```c
hook_arm64(so_find_addr("alcOpenDevice"),     (uintptr_t)alcOpenDeviceHook);
hook_arm64(so_find_addr("alcCreateContext"),  (uintptr_t)alcCreateContextHook);
```

但 `:28-39` 这两个替身里各藏了一个和掌机强相关的动作：

```c
ALCcontext *alcCreateContextHook(ALCdevice *dev, const ALCint *unused) {
  // override 22050hz with 44100hz in case someone wants high quality sounds
  const ALCint attr[] = {ALC_FREQUENCY, 44100, 0};   // ← 安卓原版写死 22050 Hz
  al_ctx = alcCreateContext(dev, attr);              // 顺手把句柄存下来，"capture context for later deinit"
  return al_ctx;
}
ALCdevice *alcOpenDeviceHook(const char *name) {
  al_dev = alcOpenDevice(name);                      // ← 同样是"存下来，退出时要关"
  return al_dev;
}
```

两个信息点：① **原版安卓为了省算力把采样率压到 22050**，移植者把它抬回 44100——
作者只留了一句注释 `in case someone wants high quality sounds`，
"掌机扛得住 44100"是我从代码选择反推的，不是他写的结论；
② 替身必须**把设备/上下文句柄私存一份**，因为游戏自己不会关——
掌机的音频设备是独占资源，退出游戏不归还，就表现为"退出后整机没声音 / 下一款游戏静音"。

同函数 `:43` 还有一行很典型：`hook_arm64(so_find_addr("InitializeCriticalSection"), (uintptr_t)ret0);`
——安卓包里混进了 Windows 风格的临界区函数，移植者直接给它一个"什么都不做、返回 0"的替身。
**"缺的函数不实现，先空转"是移植中极常见的第 3 类手段**（另外两类是 hook 换成真实现、和干脆不管返回值）。

### 必改点 ⑥：文件路径与大小写 —— 最容易被忽略、也最容易"打不开存档"的一处

安卓包里的资源名是 `MaxPayneSoundsv2.msf`（有大写）。Linux 的 ext4/FAT32 组合上，
大小写敏感行为跟固件、跟 SD 卡格式都相关。仓库的处理办法是 `src/gamedata_mapping.c`：

- `:20-43` `add_path_to_mapping()`：**键转成全小写**，值保留原始路径，塞进哈希表；
- `:49-80` `scan_directory()` 递归扫 `gamedata/` 建表；
- `:127-146` `gamedata_mapping_get()`：查的时候**把要查的路径也转成全小写**去命中。

`src/main.c` 里对应两处用法：

```c
if (gamedata_mapping_init() < 0) fatal_error("Failed to initialize gamedata mapping");
// 注释原文：Support case sensitive file systems
...
const char *file = gamedata_mapping_get(files[i]);   // check_data() 里，查不到就退回原名字
```

再配合 `strcpy((char *)so_find_addr("StorageRootBuffer"), "gamedata");`（`src/main.c`，注释
"won't save without it"）——**把游戏内部的存档根路径写死到端口目录下**。
这行漏了的症状是"能玩但一存档就报错/退出后进度没了"，掌机端口区大量帖子问的就是这个。

### 必改点 ⑦：数据从哪儿来 —— 20 行 shell 讲完"自备正版"

`port/tools/patchscript`（3,032 B）里最关键的是 `:59-76`：

```bash
unpack_apk() {
    unzip -o "$GAMEDIR/"*.apk -d "$GAMEDIR/.apktemp"
    rsync -a "$GAMEDIR/.apktemp/lib/arm64-v8a/" "$GAMEDIR/"   # ← 游戏引擎 .so 在 APK 里
    rsync -a "$GAMEDIR/.apktemp/assets/"        "$GAMEDIR/gamedata/"
}
unpack_obb() {
    unzip -o "$GAMEDIR/"*.obb -d "$GAMEDIR/.obbtemp" -x "${EXCLUDE_FILES[@]}"
    rsync -a "$GAMEDIR/.obbtemp/" "$GAMEDIR/gamedata/"        # ← 关卡/贴图/音频在 OBB 里
}
...
rsync -a "$GAMEDIR/patch/" "$GAMEDIR/gamedata/"               # 最后盖上架子自己改的补丁
```

看明白了吗——**"可执行文件"和"游戏内容"都是从你买的 APK/OBB 里拆出来的，仓库一个字节都不发。**
`:14` 那句 `LANGUAGES=("$@")` 加 `:18-31` 的 12 个语言文件排除表，是为了让你少拷 200 MB 用不到的日语俄语语音包。

## 四、构建与打包：`make package` 到底做了什么

`port/md/compile.md` 原文四条命令：

```sh
cmake .
make build     # 只出 maxpayne_arm64 这个二进制
make package   # 生成 PortMaster 规范包（顺带生成 port.json 和 README.md）
make archive   # 再压成 archive/maxpayne_arm64.zip
```

`CMakeLists.txt` 里能看到真实内容（本机实测读到的）：

- 架构开关：`ARCH_FLAGS "-march=armv8-a"`，宏 `-D__LINUX__ -D__ARM64__`；
- **钉 glibc**：`add_compile_definitions(__GLIBC_MINOR__=30)` + `-D_GLIBCXX_USE_CXX11_ABI=0`；
- 依赖用 pkg-config：`openal / sdl2 / egl / glesv2`，再手动补 `m dl stdc++ pthread`；
- `package` 目标：拷二进制 + `patch/` 目录 + `port/Max Payne.sh` + `cover.png/gameinfo.xml/screenshot.png`
  + `port/tools/`，然后
  `(cd launcher && find . -type f | sort | zip -9 -X ../package/maxpayne/launcher.love -@)`
  ——注意它把 Lua 启动器压成 **`launcher.love`**（LOVE 引擎的包格式），
  再跑三个脚本生成 `VERSION.txt` / `port.json` / `README.md`。

`scripts/generate_port_json.sh`（本机读完 39 行）逻辑特别朴素：
拿 `port/port.json` 当模板，用 `jq` 把 `attr.inst / attr.inst_md / attr.desc / attr.desc_md`
四个字段填成 `port/txt/*.txt` 和 `port/md/*.md` 的文件内容。**说明"说明文字"和"元数据"是同一份源**。

### 那道 CI 闸门值得你抄

`.github/workflows/ci.yml` 里（本机读到，行号实测）：

```yaml
# :20
runs-on: ubuntu-22.04-arm
# :52-57
MAX_GLIBC=$(objdump -T maxpayne_arm64 | grep GLIBC_ | awk '{print $5}' \
            | grep -v "^0*$" | sort -V | tail -n1)
if [ "$MAX_GLIBC" != "GLIBC_2.29" ] && [ -n "$MAX_GLIBC" ]; then
  echo "ERROR: Binary requires $MAX_GLIBC but must not exceed GLIBC_2.29"
  exit 1
fi
```

配套 `scripts/check_glibc_version.sh` 的注释直接写了失败原因清单：

```
Common causes:
  - Using sysconf() instead of getpagesize()
  - Using newer C library functions
  - Linking against newer system libraries
```

**这是"移植"和"交叉编译"的分水岭**：编出来不等于跑得起来。
目标固件的 glibc 只有 2.29，你链接时用了 2.30 才引入的符号，程序会在启动瞬间报
`version 'GLIBC_2.3x' not found` —— 于是这个项目把"最高 glibc 版本"设成构建失败的硬条件。
下一篇《02-交叉编译与打包》里我自己踩了同一堵墙，用 zig 时给出的解法不一样（见那里）。

## 五、授权与素材：仓库自己怎么说，文件又实际怎么长

按"版权结论必须落到文件级证据"的规矩，两栏分开写。

**代码授权（实测）**：根目录 `LICENSE` 首两行是 `The MIT License (MIT)` / `Copyright (C) 2021 Andy Nguyen, fgsfds`；
每个 `.c` 头注释都带 MIT 声明，`src/main.c` 里还留着 `Copyright (C) 2025 Jaakko Lukkari`。

**素材归属（实测）**：README `## Legal` 一节原文（第 100 行）：

> No assets or program code from the original game or its Android port are included in this project.
> We do not condone piracy in any way, shape or form and encourage users to legally own the original game.

这句话我做了文件级核对，**没有发现与它矛盾的证据**：

| 检查项 | 实测结果 |
|---|---|
| `patch/` 目录内容 | **只有 3 个文件**，合计 3,187,538 B：`data/menu/bitmaps/Menu_bg_Controls.tga`(3,145,772)、`data/menu/menu.txt`(28,924)、`settings.bin`(12,842) |
| 这 3 个文件是不是原版素材 | `assets/` 里有同名的**可编辑源文件**：`controls.xcf`、`cover.xcf`、`Menu_bg_Controls.jpg` ⇒ 那张 TGA 是作者自己画的操作说明背景图，不是从游戏里扒的贴图 |
| 游戏数据在哪 | 不在仓库里。`check_data()` 逐个 `stat()` 检查 8 个必需文件，缺任何一个就 `fatal_error("Could not find\n%s.\nCheck your data files.")` |
| 引擎二进制在哪 | 不在仓库里。由 `patchscript` 从用户自己的 APK 的 `lib/arm64-v8a/` 解出 |

## 六、把七处必改点收成一张表（可以拿去对任何移植项目）

| # | 必改点 | 为什么非改不可 | 本仓库的解法 | 你在别的仓库里该找什么 |
|---|---|---|---|---|
| 1 | 入口函数 | 没有 `main()`，主循环在库里 | `so_find_addr_rx` 抠 3 个符号 | `dlsym` / 符号名 / `SDL_main` |
| 2 | 加载与链接 | 运行时才知道库在哪 | 自己实现 ELF 加载 + 重定位 | `so_load`、`linker`、`LTIBind` |
| 3 | 显示后端 | 手机/主机 GPU API 不一样 | hook 4 个 EGL 函数 → SDL2+EGL+GLES2 | `egl`、`wsi`、`vulkan`、`drm/gbm` |
| 4 | 输入 | 触屏≠手柄 | SDL_GameController 轮询 + 组合键 | `input`、`controller`、`gptokeyb` 配置 |
| 5 | 声音 | 设备句柄要独占和回收 | hook `alcOpenDevice/alcCreateContext` | OpenAL/SDL_audio 初始化处 |
| 6 | 路径与大小写 | 安卓包名有大写、SD 卡不一定 | 全小写哈希表 + 改写 `StorageRootBuffer` | 资源重映射、`case`、`vfs` |
| 7 | 数据来源 | 版权不允许你分发 | shell 从用户 APK/OBB 拆包 | `instructions.md` 里的"自备原版" |

**记忆口诀：入口、加载、画面、按键、出声、路径、来源。**
