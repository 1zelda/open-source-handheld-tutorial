## 〇、先说结论：这台机器原本一个编译器都没有

我在动手前先实测了本机：

| 想要的东西 | 实测结果 |
|---|---|
| `gcc` / `g++` / `clang` / `make` / `cmake` | PATH 里**一个都没有** |
| `docker` | 没有 |
| `rustc` / `arm-none-eabi-gcc` / `aarch64-*` | 没有 |
| `wsl` | 命令在，但 `wsl -d Ubuntu` 报 `ERROR_FILE_NOT_FOUND`（`...\AppData\Local\wsl\{1c40f9a9-...}\ext4.vhdx` 不见了）；`wsl -d Ubuntu-22.04` 报 `ERROR_PATH_NOT_FOUND`。**两个发行版都是空壳，不可用** |
| C 盘剩余 | 2.6 GB（100% 占用）→ **不能往 C 盘装工具链** |
| F 盘剩余 | 1.6 TB |

结论：走 **zig**。它把"编译器 + 链接器 + 各架构的 C 库"打包成一个免安装的 zip，
一条命令就能出 ARM 二进制，不需要 Linux、不需要 Docker、不需要管理员权限。

## 二、先认识目标名字：`aarch64-linux-musl` 是什么

交叉编译的全部秘密就是这一串"三元组"：

```
  aarch64   -   linux    -   musl
  └ 指令集      └ 操作系统   └ C 运行库
```

- **指令集**：你的 XF45V 是 RK3326 = 4×Cortex-A35 = **ARMv8-A / aarch64**（64 位）。
  老一点的 32 位掌机是 `arm`（`armhf` = 硬浮点 ABI）。
- **C 运行库**决定了"这程序要不要对方机器装某个库"：
  - `musl` + `-static` → **全静态**，把 C 库整个塞进二进制，扔进任何固件都能跑；
  - `glibc`（`gnu`）→ **动态链接**，依赖对方固件里的 `libc.so.6` 和对应 glibc 版本。

`zig cc -target arm-linux-musleabihf -mcpu=help` 会把合法 CPU 名列出来；
`zig cc -V=full` 能看它实际调的是哪个 clang。

## 三、写一个真的有用的小程序：`fbcheck.c`

不讲 Hello World，讲一个**你插卡就能看出掌机通路有没有问题**的程序。
它只做三件所有移植都绕不开的事：**摸屏幕、摸按键、往屏幕涂颜色**。

代码在 `动手实践/fbcheck.c`（**3,984 B**），关键三处：

```c
/* 摸屏幕：走 framebuffer，不依赖任何图形库 */
int fd = open(dev, O_RDWR);
ioctl(fd, FBIOGET_VSCREENINFO, &vinfo);   // 拿 xres / yres / bits_per_pixel
ioctl(fd, FBIOGET_FSCREENINFO, &finfo);   // 拿 line_length / smem_len（显存总字节）

/* 摸按键：/dev/input/eventN，问内核"这台机器有没有方向键" */
ioctl(fd, EVIOCGNAME(sizeof(name)), name);              // 设备名
ioctl(fd, EVIOCGBIT(EV_KEY, sizeof(bits)), bits);       // 键位位图
has_up = (bits[KEY_UP / 64] >> (KEY_UP % 64)) & 1;      // 自己查第几位

/* 涂色：把显存 mmap 进来直接写像素 */
void *fb = mmap(NULL, screens, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
```

> 为什么选 `/dev/fb0`？上一篇里 `max_arm64/src/main.c` 的 `check_for_4x3()`
> 用的就是同一个 ioctl，同一个结构体。**移植代码里"读屏幕"这一件事，十年没变过。**

## 四、编译：四条能用的，五条翻车的（报错原文照抄）

先设变量（Git Bash）：

```bash
Z="/f/工具链/zig-x86_64-windows-0.17.0/zig.exe"
cd /f/开源掌机教程/_scratch/port_build
```

### ✅ 主力产物：64 位 ARM 全静态

```bash
"$Z" cc -target aarch64-linux-musl -static -O2 -Wall -o fbcheck_a64_musl_static fbcheck.c
```

- 第一次跑 **约 4 分钟**（zig 现场把 musl 编了一遍并缓存），第二次起 **22.3 秒**。
- 产物 **1,588,784 B**，sha256 前 16 位 `a01295fa03dcdb4c`。

### ✅ 32 位 ARM（老固件 / armhf 机器）

```bash
"$Z" cc -target arm-linux-musleabihf -mcpu=cortex_a9 -static -O2 -Wall -o fbcheck_armv7_musl_static fbcheck.c
```

产物 **1,537,812 B**，sha256 `cb6ef9630510074c…`。

### ✅ 动态链接版（只为对比，不建议发出去）

```bash
"$Z" cc -target aarch64-linux-gnu -O2 -Wall -o fbcheck_a64_gnu_default fbcheck.c
"$Z" cc -target aarch64-linux-gnu.2.17 -O2 -o fbcheck_a64_gnu217 fbcheck.c
```

两条命令产物**字节数完全一样：23,624 B**，而且 sha256 都是 `9e925e13c07a9d46…`
⇒ 说明这个 zig 对 aarch64 的默认 glibc 档位就是 **2.17**。

### ❌ 翻车 1：`-target armv7-linux-musleabihf`

```
error: unknown architecture: 'armv7'
```

`armv7` 是**架构版本**不是**架构名**。zig 的架构表里只有 `arm` / `aarch64` / `thumb`。
正确写法：`-target arm-linux-musleabihf -mcpu=cortex_a9`。

### ❌ 翻车 2：`-mcpu=cortex-a9`

```
error: unknown CPU: 'cortex'
```

zig 按 `-` 断词，把 `cortex-a9` 砍成了 `cortex`。**CPU 名要用下划线**：`cortex_a9`。

### ❌ 翻车 3：`-target aarch64-linux.2.28-gnu` 和 `.2.34-gnu`

```
error: unable to provide libc for target "aarch64-linux.2.28...7.2-gnu.2.31"
info: zig can provide libc for related target aarch64-linux.3.7.0-gnu.2.17
info: zig can provide libc for related target aarch64-linux.3.7.0-musl
```

**zig 只自带它打包过的那几个 glibc 档位。** 想钉任意 glibc 版本，zig 这条路会撞墙。
两条出路（真实项目里两种都在用）：

1. **绕开 glibc**：musl 全静态（本教程选的路，也是 PortMaster 圈子普遍选的路）；
2. **在目标同款的 Linux 里编**：`max_arm64` 用的是 `.devcontainer/Dockerfile`
   → `FROM ghcr.io/orktes/max_amd64/retro_builder:arm64`，再用 CI 闸门兜底（见第六节）。

### ❌ 翻车 4（预期内）：本机原生编译

```bash
"$Z" cc -O2 -o fbcheck_windows.exe fbcheck.c
```
```
fbcheck.c:7:10: fatal error: 'linux/fb.h' file not found
```

这不是工具链坏了：程序吃的是 **Linux 内核 ABI**，Windows 根本没有 `/dev/fb0`。

### ❌ 翻车 5：用 `zig build-exe` 编 C

```
fbcheck.c:5:10: error: 'errno.h' file not found
```

同样源码，`zig cc` 能过、`zig build-exe` 不能过——因为 `zig cc` 是完整的 **C 驱动**，
会自动挂上目标 C 库的头文件搜索路径。**编 C/C++ 就认准 `zig cc` / `zig c++`。**

## 五、编完要验货：怎么"不看机器就知道它是不是 ARM64 的"

字节数会骗人，ELF 头不会。`动手实践/` 里那个 `inspect_elf.py` 干的就是这件事，
本机实测输出（照抄）：

```
fbcheck_a64_gnu217      64位 AArch64 类型=EXEC 段数=10  动态链接=True
      PT_PHDR PT_INTERP PT_LOAD PT_LOAD PT_LOAD PT_DYNAMIC PT_GNU_RELRO PT_GNU_EH_FRAME PT_GNU_STACK PT_NOTE
fbcheck_a64_musl_static 64位 AArch64 类型=EXEC 段数=8   动态链接=False
      PT_PHDR PT_LOAD PT_LOAD PT_LOAD PT_LOAD PT_GNU_RELRO PT_GNU_EH_FRAME PT_GNU_STACK
fbcheck_armv7_musl_static 32位 ARM32 类型=EXEC 段数=6   动态链接=False
      PT_PHDR PT_LOAD PT_LOAD PT_LOAD PT_GNU_STACK 0x70000001
```

再看二进制里的字符串（同一份脚本的输出）：

```
== gnu217 (动态) ==
  INTERP : ['/lib/ld-linux-aarch64.so.1']
  .so 串 : ['libc.so.6']
  GLIBC 版: ['GLIBC_2.17']
== musl 静态 aarch64 ==
  .so 串 : []      INTERP : []      GLIBC 版: []
```

**读法**：

| 字段 | 看什么 | 静态版 | 动态版 |
|---|---|---|---|
| `e_ident[4]` | 位宽：2=64 位，1=32 位 | 2 | 2 |
| `e_machine` | 183=AArch64，40=ARM32 | 183 | 183 |
| `PT_INTERP` | 有 = 启动时要找动态加载器（**对方必须有对应 glibc**） | **无** | `/lib/ld-linux-aarch64.so.1` |
| `PT_DYNAMIC` | 有 = 运行时依赖别的 `.so` | **无** | 有，NEEDED = `libc.so.6` |
| `GLIBC_x.y` 串 | 用到的最高 glibc 版本 | **无** | `GLIBC_2.17` |
| 体积 | 静态把 C 库背身上 | **1,588,784 B** | **23,624 B** |

体积差 **67 倍**。这就是"静态到处能跑但大、动态小但挑机器"的量化版本。

三个字节级校验动作，建议你每次移植都走一遍：
1. 打开文件读 `e_machine`，确认 183（别把 armv7 的包装进 aarch64 端口）；
2. 确认**没有** `PT_INTERP`（想全兼容就别留）；
3. 全静态的话确认 `.so 串` 为空。

`max_arm64` 里其实有同样的架构自检：`src/so_util.c:221` 验 `ELFCLASS64`、`:227` 验
`e_machine != EM_AARCH64` 就报错 —— **它 load 你的 .so 时用的判据，和你验自己产物用的是同一套。**

### 附：我自己在这段代码上翻过一次车（值得记住）

数 ELF 段数时我把 `e_phnum` 读在了**偏移 60**。实测（`fbcheck_a64_musl_static`）：

```
偏移56(=e_phnum 正确)      8
偏移60(我一开始读错的那个)  22      ← 那是 e_shnum（节头数量），不是段数
```

所以第一版输出里冒出一堆 `0x69006c6c=5066066896500116992` 这种鬼东西——
那是拿 22 去循环、越界把节头和字符串当段解了。ELF64 头里顺序是
`e_ehsize@52, e_phentsize@54, e_phnum@56, e_shentsize@58, e_shnum@60`；
ELF32 是 `phentsize@42, phnum@44`。**别记"偏移"，记"紧跟在 phentsize 后面的是 phnum"。**

## 六、glibc 闸门：编出来 ≠ 跑起来，得有人拦着

真实项目用两道闸：

**闸门 A（构建侧，CI 拦）** —— `max_arm64/.github/workflows/ci.yml:52-57`：

```bash
MAX_GLIBC=$(objdump -T maxpayne_arm64 | grep GLIBC_ | awk '{print $5}' \
            | grep -v "^0*$" | sort -V | tail -n1)
if [ "$MAX_GLIBC" != "GLIBC_2.29" ] && [ -n "$MAX_GLIBC" ]; then
  echo "ERROR: Binary requires $MAX_GLIBC but must not exceed GLIBC_2.29"; exit 1
fi
```

`scripts/check_glibc_version.sh` 里那句注释值得贴在墙上：

```
Common causes:  - Using sysconf() instead of getpagesize()
                - Using newer C library functions
                - Linking against newer system libraries
```

（对照一下：我这篇教程里的 C 程序就用了 `sysconf(_SC_PAGESIZE)`。
在 zig musl 静态下它不产生任何 `GLIBC_*` 引用，所以没事；
但**同样的源码在 glibc 上编，就会带上高版本符号**——这就是那条注释的由来。）

**闸门 B（安装侧，PortMaster 拦）** —— 本机 clone 的
`02-模拟器库/已clone仓库/R36S专用/PortMaster-GUI/PortMaster/pylibs/harbourmaster/harbour.py:1164-1168`：

```python
min_glibc = port_info.get('attr', {}).get('min_glibc', "")
if min_glibc not in ("", None) and isinstance(min_glibc, str):
    if version_parse(min_glibc.strip()) > version_parse(self.device['glibc']):
        return False
```

**把它 `port.json` 里的 `min_glibc` 填成 "2.31"，PortMaster 就不会把这包装到 glibc 更老的机器上，
连下载列表里都不给你看。** 这就是"防止用户拿到跑不起来的包"的机制层答案。
（顺带一个冷知识：`max_arm64` 自己的 `port/port.json` 里 `"min_glibc": ""` 是空的，
它完全靠闸门 A 保证安全。）

## 七、打包：PortMaster 到底认哪些字段

规范不是文档里的口头约定，它就是一段 Python 的默认值表。
本机读到 `harbourmaster/info.py:18-40`（原文）：

```python
PORT_INFO_ROOT_ATTRS = {
    'version': 4,
    'name': None,
    'items': None,
    'items_opt': None,
    'attr': {},
    }

PORT_INFO_ATTR_ATTRS = {
    'title': "", 'desc': "", 'inst': "", 'genres': [], 'porter': [],
    'image': {}, 'rtr': False, 'exp': False, 'runtime': [],
    'min_glibc': "", 'reqs': [], 'arch': [],
    }
```

**顶层 5 个键 + `attr` 里 12 个键，一个都不能拼错**（拼错了会被默认值覆盖，或安装时报错）。

三个真正决定"这包装不装得上、要不要自备游戏"的字段：

| 字段 | 谁读它（file:line） | 作用 |
|---|---|---|
| `items` | `harbour.py:633`（`item.casefold().endswith('.sh')`） | 声明 zip 里顶层有什么；**必须以 `.sh` 认启动脚本** |
| `arch` | `harbour.py:1179-1182` 拼成需求，和 `device_info.txt:917` 造出来的 `CAPS`（含 `DEVICE_ARCH`，见 `:178-182`）做 `match_requirements` | 32 位机器看不到 aarch64-only 的包 |
| `rtr` | `pugscene.py:2229` 标签写死 `"rtr": _("Ready to Run")`，`harbour.py:2458`/`source.py:384` 双向换算成 `runtype="rtr"` | **Ready To Run = 不需要自备原版数据**。马克思佩恩那种填 `false` |

`max_arm64/port/port.json` 实测内容：`"version":4, "name":"maxpayne.zip",
"items":["Max Payne.sh","maxpayne"], "arch":["aarch64"], "availability":"paid",
"rtr":false, "exp":false, "min_glibc":""`，还多带一个 `store[]` 指向 Google Play。
**`availability":"paid"` + `"rtr":false` 就是"这游戏要你自己买"的两道声明。**

```bash
./fbcheck_a64_musl_static            # 只看探测
./fbcheck_a64_musl_static --green    # 真把屏幕涂绿
```

**成功长什么样**：打印出 `1024x768`、bpp、`line_length`、显存字节数，
以及 `/dev/input/eventN` 的设备名和"有方向键=是"。
XF45V 正常应给到 1024×768；如果你看到 640×480，那说明你在 R36S 之类的机器上，不是这台。

**失败先看一个文件**：`/roms/ports/fbcheck/log.txt`
（脚本里 `exec > >(tee -a "$GAMEDIR/log.txt") 2>&1` 就是为这个）。
掌机端口 90% 的问题都只能从这里读出来，屏幕上只会一闪退回前端。

## 十、边界（这一节不许跳过）

- ✅ 可以：自己写 C、交叉编译、打包成端口、自己机器上玩、把**你自己的代码**发出去。
- ✅ 可以：下载别人**开源**的移植工程源码来读、来编译（前提是他仓库里不含原版素材——
  核对方法见上一篇第五节：数文件、看 `assets/`、读 README 的 Legal 段）。
- ❌ 不可以：把别人工程**构建出来的成品游戏包**（含商业游戏引擎/资源）上传、分发、镜像。
  本库有条规矩：**通用引擎/播放器/模拟器/前端收成品；某一款游戏的静态重编译体只收源码。**
  我自己违反过一次（收了个 Switch 重编译 `.nro`），复核后删文件退台账，
  全过程记在 `交接稿-项目目标与现状.md` §六 口径 15。
- ❌ 不可以：把商业 ROM/BIOS/APK/OBB 打包进端口一起发。
  正确做法就是 `patchscript` 那种：**让脚本去用户自己的文件里拆**，仓库只发代码。
